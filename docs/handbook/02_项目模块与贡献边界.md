# 项目模块与贡献边界

最后更新：2026-07-31

本文回答三个问题：

1. 项目由哪些模块组成，每个模块的输入、输出和状态是什么；
2. 每个模块尝试过哪些方案，为什么保留当前方案；
3. 哪些是官方RNNoise资产、论文算法复现、自主工程实现或自主消融。

最终性能数字统一见
[06_结果与结论说明.md](06_结果与结论说明.md)，实验转折和失败证据见
[05_实验路线与失败分析.md](05_实验路线与失败分析.md)。

## 1. 系统边界

本项目实现的是实时单通道noise suppression：

```text
16 kHz/48 kHz mono noisy audio
→ 输入检查与流式buffer
→ 经典DSP baseline 或 RNNoise
→ 长度、采样率一致的enhanced audio
→ VAD/延迟/RTF/客观指标/试听诊断
```

它在完整通信前端中的位置大致为：

```text
麦克风 → AEC/Beamforming（若有）→ 本项目：Noise Suppression
       → AGC/Limiter → Codec、通话上行或ASR
```

项目不把AEC、Beamforming、ANC、Source Separation或ASR算作已实现模块。

## 2. 归属标签

本文使用四类标签，避免把“代码由自己写”误说成“算法由自己发明”：

| 标签 | 含义 |
|---|---|
| **官方/第三方** | 直接使用外部代码、预训练权重或库实现 |
| **论文复现** | 算法思想和公式来自公开文献，项目自行编写Python实现和测试 |
| **自主工程** | 为数据、流式状态、接口、对齐、评价或Demo独立完成的系统工作 |
| **自主消融** | 项目提出并验证的控制策略；属于工程实验，不声称新的论文理论 |

“自主实现”只说明代码和系统集成由项目完成，不等于原创STFT、Wiener、MCRA等已有算法。

## 3. 模块总图

```text
                  ┌─ Classical branch ─────────────────────────────────────┐
Audio/Data I/O ──→ STFT/WOLA → Noise PSD → Wiener/OM-LSA ────────────────┼─→ Metrics
      │                 └→ VAD probability → A5 soft prior（仅该消融使用）─┘      │
      │                                                                        ├→ Plots
      └→ 16→48 kHz FIR → RNNoise C state → 48→16 kHz FIR ─→ R4/C1 ───────────┤
                                                                               └→ Demo
```

当前正式输出选择RNNoise R3。经典分支用于解释、对照和失败定位；R4/C1保留为可复现负结果，
不属于默认路径。

## 5. 模块一：Audio I/O、数据准备与输入契约

| 项目 | 内容 |
|---|---|
| 输入 | WAV路径，或一维浮点audio array与sample rate |
| 输出 | `AudioData(samples, sample_rate)`、processed pair、JSONL manifest |
| 状态 | 音频读写本身无跨帧状态；dataset preparation维护pair/split元数据 |
| 主要方案 | SoundFile读写；按stem配对；paired polyphase resampling |
| 当前选择 | 内部统一float mono；数据集链路统一16 kHz |
| 原因 | 保持clean/noisy共同尺度和严格对齐，便于侵入式评价 |
| 代码位置 | [`audio.py`](../../src/speech_frontend/audio.py)、[`dataset.py`](../../src/speech_frontend/dataset.py)、[`prepare_voicebank.py`](../../scripts/prepare_voicebank.py) |
| 归属 | 自主工程；数据来自官方VoiceBank + DEMAND |

关键约束：

- 音频必须是一维、浮点、有限值；
- 多声道直接拒绝，不静默downmix；
- clean/noisy采样率和shape必须完全相同；
- 不对clean/noisy分别归一化；
- 输出长度和采样率是后续模块的硬契约。

这一模块看似简单，但pair错位、独立归一化或错误采样率都会让后面的Oracle、SI-SDR和
noise residual分析失效。

## 6. 模块二：Framing、STFT/iSTFT与Streaming WOLA

| 项目 | 内容 |
|---|---|
| 输入 | 16 kHz一维时域波形或任意长度chunk |
| 输出 | frame-major complex spectrum，或重建的时域样本 |
| 状态 | analysis buffer、OLA signal、OLA normalization、累计输入/输出、flush状态 |
| 主要方案 | 512-sample frame、128-sample hop、512-point FFT、sqrt periodic Hann |
| 当前选择 | normalized weighted overlap-add；离线和streaming使用同一变换定义 |
| 原因 | 精确重建、增益施加在复数频谱、支持任意chunk |
| 代码位置 | [`framing.py`](../../src/speech_frontend/framing.py)、[`stft.py`](../../src/speech_frontend/stft.py)、[`streaming.py`](../../src/speech_frontend/streaming.py) |
| 归属 | 标准DSP的自主实现 |

尝试和验证重点：

- A0 identity先验证`iSTFT(STFT(x))≈x`，再引入增强算法；
- `StreamingWOLA`只在一个hop的OLA值不会再变化时输出；
- `flush()`补齐尾部并裁回准确输入长度；
- `reset()`必须清空buffer和生命周期状态；
- processor必须保持spectrum shape且不能产生NaN/Inf。

选择这套实现不是因为STFT本身新颖，而是为了控制边界、延迟和数值行为，不把关键状态
隐藏在黑盒离线函数里。

## 7. 模块三：VAD

| 项目 | 内容 |
|---|---|
| 输入 | 16 kHz mono speech/noise waveform |
| 输出 | speech probability、frame label和speech segments |
| 状态 | noise floor或noise PSD、上一帧DD项、onset/offset计数、hangover状态 |
| 尝试方案 | Adaptive Energy VAD、Sohn-style Statistical VAD、WebRTC VAD |
| 当前选择 | 独立VAD任务选择Statistical VAD；经典A5将其作为soft prior；WebRTC只作外部对照；R3使用RNNoise自身VAD输出 |
| 原因 | Statistical VAD比纯能量门限更能描述speech/noise不确定性；R1与R3都不依赖额外hard VAD gate |
| 代码位置 | [`vad/`](../../src/speech_frontend/vad)、[`evaluate_vad.py`](../../scripts/evaluate_vad.py) |
| 归属 | Energy为自主baseline；Statistical为论文复现；WebRTC为第三方 |

### 7.1 Adaptive Energy VAD

主要组件：

- 20 ms frame、10 ms hop；
- 短时RMS/log energy；
- 滑动低分位数和EWMA noise floor；
- on/off双阈值；
- onset、minimum speech、pre-roll和hangover状态机。

优点是快、可解释；缺点是高能噪声容易误触发、低声语音容易漏检。

### 7.2 Statistical VAD

主要组件：

- `H0: noise only`和`H1: speech + noise`；
- posterior/prior SNR；
- decision-directed平滑；
- 80～4000 Hz范围的log-likelihood聚合；
- 连续speech probability；
- 与Energy VAD共用最终状态机。

项目保留概率、score和二值状态三层输出，避免把hard decision直接当作所有后续模块的真值。

### 7.3 WebRTC VAD

WebRTC VAD通过第三方Python binding接入，只用于相同受控VAD数据上的外部baseline。
aggressiveness在dev选择，holdout不再改。不能把它写成项目自研模块。

## 8. 模块四：Noise PSD estimation

| 项目 | 内容 |
|---|---|
| 输入 | 每帧complex spectrum或power spectrum |
| 输出 | 每个时频点的noise PSD与speech-presence probability |
| 状态 | 平滑谱、局部最小值窗口、previous PSD/SPP、IMCRA子窗状态 |
| 尝试方案 | MCRA、IMCRA；Oracle noise PSD用于排错 |
| 当前选择 | MCRA配合OM-LSA保留为经典R1；R3不单独调用此模块 |
| 原因 | MCRA更简单稳定；IMCRA在关键结构噪声上反而严重低估noise PSD |
| 代码位置 | [`noise/mcra.py`](../../src/speech_frontend/noise/mcra.py)、[`noise/imcra.py`](../../src/speech_frontend/noise/imcra.py) |
| 归属 | 经典论文算法的自主Python复现 |

### 8.1 MCRA

MCRA通过时间平滑、局部谱最小值和频点级speech-presence probability控制noise PSD更新。
核心设计是软更新，而不是：

```text
VAD=False → 更新
VAD=True  → 完全冻结
```

### 8.2 IMCRA

IMCRA加入两阶段平滑、频率邻域、subwindow minimum和bias compensation。理论上更完整，
但在固定金属结构噪声样本中，大量时频点被判断为speech presence，使noise PSD低估更严重。

### 8.3 Oracle

paired数据允许计算：

```text
true_noise = noisy - clean
```

Oracle Wiener不可部署，只回答“如果noise PSD正确，当前STFT/gain表示是否有能力去掉该
噪声”。Oracle明显有效，说明经典路线的主要瓶颈是speech/noise estimation，而不是
STFT不能表示。

## 9. 模块五：经典频域增强

| 项目 | 内容 |
|---|---|
| 输入 | noisy complex spectrum、estimated noise PSD、可选SPP/VAD probability |
| 输出 | enhanced complex spectrum、gain与诊断trace |
| 状态 | DD prior SNR、previous gain/enhanced power、增益平滑状态 |
| 尝试方案 | Spectral Subtraction、instantaneous Wiener、DD-Wiener、Dual-Uncertainty、OM-LSA |
| 当前选择 | MCRA + OM-LSA作为可解释经典baseline；不作为最终默认 |
| 原因 | 比简单Wiener更好地表达speech-presence uncertainty，但仍不能识别关键结构噪声 |
| 代码位置 | [`enhancement/`](../../src/speech_frontend/enhancement)、[`pipeline.py`](../../src/speech_frontend/pipeline.py) |
| 归属 | Spectral Subtraction/Wiener/OM-LSA为论文复现；Dual-Uncertainty为自主消融 |

路线作用：

- **A0 Identity**：验证输入输出、STFT重建和指标；
- **A1 Spectral Subtraction**：最简单减谱baseline，展示hard spectral gain的伪影风险；
- **A3 Instantaneous Wiener**：隔离noise estimator作用，但gain随帧变化较快；
- **A4 DD-Wiener**：用上一帧增强结果平滑prior SNR；
- **A5 Dual-Uncertainty**：把noise update的`p_N`和gain control的`p_G`分开；
- **A6 gain smoothing/startup ramp**：尝试降低时频增益突变；
- **A7 MCRA + OM-LSA**：经典路线中保留的R1；
- **A8 IMCRA + OM-LSA**：更复杂估计器未解决结构噪声，保留负结果。

Dual-Uncertainty属于项目的工程设计，但实验没有显示稳定优势，所以不能写成“最终创新算法”。

| 项目 | 内容 |
|---|---|
| 输入 | 48 kHz mono，每次480 samples；C API使用16-bit PCM量级的float buffer |
| 输出 | 480-sample enhanced frame和一个VAD probability |
| 状态 | 官方`DenoiseState`内部的GRU、pitch、overlap和历史gain状态 |
| 主要方案 | 官方DSP feature/pitch frontend＋预训练causal neural estimator＋DSP synthesis |
| 当前选择 | R3 official RNNoise |
| 原因 | 能利用跨帧与pitch/频带结构识别统计方法误判的结构化噪声，同时满足实时约束 |

- 项目使用官方C API，而不是在Python中重写模型；

详细网络和DSP结构见

## 11. 模块七：RNNoise C API与实时流式适配

| 项目 | 内容 |
|---|---|
| 输入 | 48 kHz或16 kHz normalized float mono，外部chunk长度任意 |
| 输出 | 同采样率、最终同长度的enhanced audio和帧级VAD |
| 状态 | C `DenoiseState`、input buffer、FIR history、downsample phase、计数器和flush状态 |
| 主要方案 | persistent C state、arbitrary-chunk buffer、causal 16↔48 kHz FIR |
| 当前选择 | `StreamingRNNoise48k`与`StreamingRNNoise16k` |
| 原因 | 官方API固定48 kHz/480 samples，而文件、声卡和上游服务不保证相同chunk边界 |
| 代码位置 | [`rnnoise/backend.py`](../../src/speech_frontend/rnnoise/backend.py)、[`rnnoise/streaming.py`](../../src/speech_frontend/rnnoise/streaming.py)、[`rnnoise/resampler.py`](../../src/speech_frontend/rnnoise/resampler.py) |
| 归属 | 自主实时工程；FIR与缓冲思想是标准工程方法 |

### 11.1 C API幅值契约

项目外部统一使用`[-1, 1]`normalized float，但RNNoise的`float*`实际采用16-bit PCM幅值：

```text
normalized input × 32767
→ rnnoise_process_frame
→ output ÷ 32767
```

忽略这一步会使模型看到错误能量尺度。

### 11.2 Persistent state

每条stream只创建一次`DenoiseState`。若每个chunk重置，GRU、pitch和overlap历史会丢失，
输出会依赖应用层chunk边界。

### 11.3 Arbitrary chunks

外部可以输入1、137、480、1000或其他长度。内部先缓存，凑满480个48 kHz样本才调用一次
RNNoise。`flush()`处理不足一帧的尾部并保证最终输出长度等于输入长度。

### 11.4 16↔48 kHz adapter

16 kHz路径使用127-tap Kaiser FIR：

```text
16 kHz → zero insertion ×3 → anti-imaging FIR
       → RNNoise 48 kHz
       → anti-alias FIR → decimation ÷3 → 16 kHz
```

FIR history和decimation phase跨chunk保存，避免分块重采样边界不连续。16 kHz路径测得固定
对齐延迟为202 samples/12.625 ms；原生48 kHz RNNoise核心为一帧、约10 ms。实时系统不能
消除物理延迟，只能报告并在离线成对评价时补偿。

更完整的状态、延迟和测试说明见
[04_实时工程实现与测试.md](04_实时工程实现与测试.md)。

## 12. 模块八：R4与C1后处理controller

| 项目 | 内容 |
|---|---|
| 输入 | 对齐的noisy、R3 enhanced、RNNoise VAD |
| 输出 | controller audio和逐帧strength/boost诊断 |
| 状态 | 平滑能量、previous strength或voiced envelope |
| 尝试方案 | fixed residual mix、VAD-aware mix、correction-aware mix、output-only continuity |
| 当前选择 | 全部不替换R3；只作为负结果和试听消融 |
| 原因 | R4重新引入原始结构噪声；C1总体没有稳定改善 |
| 代码位置 | [`rnnoise/controller.py`](../../src/speech_frontend/rnnoise/controller.py)、[`rnnoise/continuity.py`](../../src/speech_frontend/rnnoise/continuity.py) |
| 归属 | 自主消融 |

### 12.1 R4 residual mixing

R4试图把被RNNoise过度抑制的语音混回来：

```text
output = strength × RNNoise + (1-strength) × noisy
```

还尝试根据VAD或`noisy-enhanced`correction energy调整strength。客观均值可以改善，但
原始noisy中的金属结构噪声也被一起混回，固定试听未通过，因此time-domain residual mixing
路线关闭。

### 12.2 C1 continuity

C1不加入raw noisy，只在“高VAD且R3输出电平突然下降”的帧，对已经存在的输出施加最多
3/6 dB包络增益。它避免直接恢复原噪声，但不能恢复RNNoise已完全删除的语音。6 dB配置淘汰，
3 dB只保留为试听探针。

  delay、controller、flush/reset和clipping。

## 14. 为什么最终选择R3

选择过程不是“深度模型一定优于传统方法”，而是一条逐步排错的证据链：

```text
STFT identity正确
→ 经典Wiener/OM-LSA能降低一部分宽带噪声
→ 关键结构噪声仍然存在
→ Oracle Wiener能去掉它
→ 说明频谱表示和gain机制有能力
→ MCRA/IMCRA把结构噪声误判为speech presence
→ 需要利用pitch和跨帧模式的学习型判别
→ RNNoise R3去除了关键金属噪声
→ R4虽改善部分指标，却把原噪声混回
→ C1没有稳定改善
→ 当前保持R3，并明确记录轻微speech over-suppression
```
