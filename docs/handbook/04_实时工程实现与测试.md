# 实时工程实现与测试

最后更新：2026-07-31

## 1. 从模型推理到实时系统

能够调用一次 RNNoise 函数，不等于已经实现实时语音前端。真实音频流存在以下工程问题：

- 麦克风或应用传入的 chunk 大小不一定是 480；
- 神经网络、pitch、频谱重叠等状态必须跨帧延续；
- 数据集常用 16 kHz，而 RNNoise 固定运行在 48 kHz；
- C API 和 Python 音频的幅值约定不同；
- 算法存在固定延迟，评价时必须正确对齐；
- 流结束时还存在不足一帧的输入和无法生成的延迟尾部；
- 平均处理速度足够快，不代表每个声卡 callback 都一定按时完成。

本项目在官方 C 推理内核外实现了完整的流式适配层：

```text
16 kHz 或 48 kHz normalized mono chunks
  ↓
输入校验与幅值转换
  ↓
可选：16→48 kHz 状态化 FIR
  ↓
任意 chunk 缓冲为 480-sample frames
  ↓
持久化 RNNoise DenoiseState
  ↓
处理首帧延迟、flush 和尾部长度
  ↓
可选：48→16 kHz 状态化 FIR
  ↓
等长增强音频、VAD、延迟和运行统计
```

主要实现位于：

```text
src/speech_frontend/rnnoise/backend.py
src/speech_frontend/rnnoise/streaming.py
src/speech_frontend/rnnoise/resampler.py
```

## 2. Persistent state：为什么状态必须持久化

`RNNoiseLibrary` 负责加载共享库并声明 C 函数签名；`RNNoiseState` 拥有一个
`DenoiseState` 指针。一个连续音频流只创建一次 state，并对所有后续帧重复调用：

```text
rnnoise_create()
  ↓
process frame 0
  ↓
process frame 1
  ↓
...
  ↓
process frame N
  ↓
rnnoise_destroy()
```

`DenoiseState` 内部包含的不只是神经网络 hidden state，还包括：

- Conv1D 的历史输入；
- 三层 GRU 的 recurrent state；
- pitch 搜索历史；
- analysis/synthesis overlap；
- delayed spectrum；
- 上一帧频带增益；
- 滤波器和特征提取所需历史。

如果每个 10 ms 帧都重新执行 `rnnoise_create()`，会产生三个问题：

1. GRU 无法利用跨帧语音和噪声上下文；
2. pitch、overlap 和上一帧增益被清空，帧边界可能不连续；
3. 输出不再等价于官方连续流处理。

因此“持久化 state”不是性能优化，而是算法正确性要求。

### 2.1 资源所有权

`RNNoiseState` 提供：

- `close()`：释放 C state，重复调用安全；
- context manager：退出 `with` 时自动释放；
- `reset()`：销毁旧 state 并创建全新 state；
- closed-state 检查：释放后继续处理会抛出错误。

这避免长期实时服务中的 native memory 泄漏和悬空指针使用。

## 3. Python/C API 的音频契约

项目内部音频约定为：

```text
单声道
一维数组
有限数值，不允许 NaN/Inf
float audio ∈ [-1, 1]
```

而 RNNoise C API 使用 16-bit PCM magnitude 的浮点缓冲区。`process_frame()` 的转换为：

```text
normalized input
→ float64 × 32767
→ round
→ int16
→ float32 PCM magnitude
→ rnnoise_process_frame()
→ output / 32767
→ normalized float32
```

输入超过 `[-1, 1]`、含非有限值或不是恰好 480 个 48 kHz 样本时，接口会立即拒绝，
而不是把错误数据静默传入 C 层。

### 3.1 `pcm_compatible` 模式

正常 API 保留 C 核心返回的浮点结果。为了与官方 raw-PCM 命令行程序逐样本比较，测试模式
还会将输出：

```text
clip to [-32768, 32767]
→ cast to int16
→ convert back to normalized float
```

这样可以把算法差异和 PCM 量化差异分开定位。

## 4. Arbitrary-chunk streaming

RNNoise 每次必须处理 480 个 48 kHz 样本，但外部系统可能传入任意长度：

```text
1、127、137、480、1000、4096 ... samples
```

`StreamingRNNoise48k` 使用内部 `_input_buffer` 保存尚未凑满一帧的样本：

```text
process_chunk(chunk)
  ↓
追加到 input buffer
  ↓
while buffer >= 480:
    取出前 480 点
    调用同一个 RNNoiseState
    保存输出和 VAD
  ↓
返回本次已经可以产生的完整输出帧
```

因此应用层不需要为了适配模型而强制声卡或网络每次都提供480个样本。

### 4.1 Chunk invariant

对同一段波形，以下两种方式必须产生逐样本相同的结果：

```text
一次传入完整波形
```

和

```text
按 [1, 127, 480, 3, 1001, 19, ...] 任意切分后依次传入
```

这称为 chunk invariance。测试同时比较音频输出和 VAD 序列，确保 chunk 边界不会改变
模型状态或重采样相位。

### 4.2 首帧为什么不立即输出

RNNoise 在处理当前帧时合成上一帧 delayed spectrum。第一帧之前不存在有效的上一帧，
因此流式封装丢弃第一次 C 输出：

```text
输入第 1 个 480-sample frame → 只完成 priming，输出 0 samples
输入第 2 个 480-sample frame → 输出第 1 帧增强结果
```

这与官方命令行 demo 丢弃第一处理帧的行为一致，也使核心延迟明确为 480 samples。

### 4.3 VAD 与音频的时序关系

`rnnoise_process_frame()` 返回的 VAD 概率来自当前输入特征，而同一次调用产生的有效音频
对应 delayed frame。因而不能天然假设“返回数组中的第 i 个 VAD”与“刚输出的第 i 个
音频帧”零延迟对齐。

只记录 VAD trace 时影响不大；若要用 VAD 控制后处理增益，则必须明确是否要把 VAD 延迟
一帧。否则控制器可能使用下一帧的语音概率调节上一帧音频。

## 5. 16↔48 kHz 状态化 FIR 重采样

RNNoise 原生只处理 48 kHz，而项目中的 VoiceBank + DEMAND 音频和许多语音识别前端使用
16 kHz。`StreamingRNNoise16k` 的路径是：

```text
16 kHz input
→ StreamingUpsampler3
→ 48 kHz RNNoise
→ StreamingDownsampler3
→ 16 kHz output
```

### 5.1 FIR 规格

上下采样器使用同一组低通 FIR：

| 参数 | 数值 |
|---|---:|
| 插值/抽取比例 | 3 |
| FIR taps | 127 |
| 截止频率 | 7,800 Hz |
| 设计方法 | `firwin` |
| 窗函数 | Kaiser，`β = 8.6` |
| 单个 FIR 群延迟 | 63 samples @ 48 kHz |

截止频率略低于16 kHz信号的Nyquist频率8 kHz，为过渡带留出空间。

### 5.2 16→48 kHz

上采样流程：

1. 每个16 kHz样本后插入两个零；
2. FIR去除插零产生的频谱镜像；
3. 系数乘以3，补偿插零造成的幅值比例；
4. 保存前一chunk的126点filter state。

升采样只增加采样点，不会创造原始16 kHz音频中8 kHz以上的真实声学信息。它的作用是让
信号满足RNNoise接口，并保持原有0～8 kHz内容。

### 5.3 48→16 kHz

下采样流程：

1. FIR抑制8 kHz以上、抽取后会产生aliasing的频率；
2. 每3点保留1点；
3. 保存126点filter state；
4. 保存decimation phase。

代码通过累计的`total_input_samples`计算每个chunk的第一个抽取位置：

```text
first_index = (-total_input_samples) mod 3
```

如果不保存phase，每个chunk都从索引0抽取，不同chunk长度会让输出相位错位，结果也不再
chunk invariant。

### 5.4 为什么不能逐chunk调用离线重采样

对每个chunk独立执行离线重采样会反复假设chunk两侧不存在历史，造成：

- 边界瞬态；
- FIR历史丢失；
- 抽取phase重置；
- 输出长度累计误差；
- 改变chunk大小时输出变化。

状态化FIR使整个音频流等价于一次连续因果滤波。

### 5.5 重采样的clipping保护

16→48 kHz FIR在瞬态处可能产生轻微overshoot。代码统计超过`[-1, 1]`的样本数，并在进入
RNNoise前进行clip。该计数被保留为诊断信息，不能只clip后假装从未发生过越界。

## 6. 延迟：202 samples / 12.625 ms 从哪里来

### 6.1 原生48 kHz链路

RNNoise核心延迟是一帧：

```text
480 samples / 48,000 Hz = 10 ms
```

### 6.2 16 kHz链路

上下两个127-tap FIR各有63个48 kHz样本的群延迟：

```text
两段 FIR：2 × 63 = 126 samples @ 48 kHz
换算到16 kHz：126 / 3 = 42 samples
```

RNNoise一帧延迟换算到16 kHz：

```text
480 / 3 = 160 samples
```

总固定算法延迟：

```text
160 + 42 = 202 samples @ 16 kHz
202 / 16,000 = 12.625 ms
```

### 6.3 延迟不是处理耗时

必须区分：

- **算法延迟**：算法结构决定的时间偏移，本项目16 kHz链路为12.625 ms；
- **计算耗时**：CPU实际完成一次处理需要多久；
- **组帧等待**：chunk不足480点时等待后续输入的时间；
- **设备缓冲延迟**：声卡输入/输出buffer；
- **调度延迟**：线程、queue和操作系统调度。

即使处理耗时趋近于零，算法延迟仍然存在。实时系统只能报告和管理它，不能通过离线裁剪在
物理上让声音提前出现。

### 6.4 对齐错误的诊断

项目早期只补偿了重采样的42 samples，遗漏RNNoise核心的160 samples。30条dev样本的平均
SI-SDRi因此错误地变成：

```text
-28.109 dB
```

随后分别计算增强输出相对clean、noisy和离线reference的互相关峰值：

- 未补偿16 kHz流输出相对clean/noisy滞后202 samples；
- 相对使用零相位离线重采样的CLI wrapper滞后42 samples；
- 补偿完整202 samples后，关键样本结果恢复为合理正值。

这说明评价中的时间对齐和算法本身同等重要。约10 ms的固定错位就可能让波形指标看起来
像算法完全失效。

## 7. Flush、reset 与 close

### 7.1 `flush()`

流结束时，内部可能还剩不足一帧的输入。48 kHz封装会：

1. 将不足480点的最后一帧补零；
2. 处理所有能够产生的有效延迟帧；
3. 对未来帧不存在、无法生成的尾部补零；
4. 保证最终输出长度严格等于输入长度；
5. 关闭C state并将流标记为flushed。

16 kHz封装随后把剩余48 kHz输出送入downsampler，并硬性检查：

```text
total_output_samples == total_input_samples
```

第二次调用`flush()`返回空数组，属于幂等操作；`flush()`之后再调用`process_chunk()`会
报错，避免把两个逻辑音频流误接在同一状态上。

尾部补零是“保持文件长度”的工程选择，并不代表系统能够在没有未来输入的情况下推理出
最后一个延迟帧。

### 7.2 `reset()`

`reset()`用于在同一个对象上开始一条全新的音频流。它会重置：

- C层`DenoiseState`；
- 48 kHz输入buffer；
- primed/flushed标志；
- 输入输出计数；
- 两段FIR filter state；
- downsampling phase；
- clipping计数。

重置后处理同一波形，应与新创建对象逐样本一致。

### 7.3 `close()`

`close()`只负责释放native资源，不对剩余输入执行补帧或生成尾部。正常需要完整输出时应先
使用`flush()`；异常退出或不再关心尾部时可以直接`close()`。

## 8. 官方CLI与项目API等价验证

等价验证的目标不是证明Python代码“看起来差不多”，而是排除以下差异：

- 输入量化尺度错误；
- 每帧重置state；
- 首帧延迟处理不同；
- 输出int16截断方式不同；
- chunk边界改变结果。

测试流程：

1. 生成合法的归一化测试信号；
2. 转成little-endian int16 raw PCM；
3. 使用官方`rnnoise_demo`处理；
4. 使用项目C API wrapper的`pcm_compatible=True`处理；
5. 去掉API输出的首个480-sample delayed frame；
6. 对剩余PCM执行逐样本相等断言。

验证结果表明，在使用相同PCM量化并正确处理首帧后，项目API与官方CLI输出逐样本一致。

流式封装还额外验证：

- 任意chunk输出与单chunk输出相同；
- 流式结果的有效部分与CLI相同；
- 因缺少未来帧而不能生成的尾部按约定补零；
- 最终输出长度与输入严格一致。

## 9. RTF 与实时性判断

RTF（Real-Time Factor，实时因子）定义为：

```text
RTF = 处理耗时 / 音频时长
```

例如处理10秒音频用了0.5秒：

```text
RTF = 0.5 / 10 = 0.05
```

解释：

- `RTF < 1`：平均速度快于音频产生速度，具备实时运行的必要条件；
- `RTF = 1`：平均处理耗时等于音频时长；
- `RTF > 1`：输入积压，无法持续实时。

本项目R3在dev上的mean/median RTF约为：

```text
0.057 / 0.048
```

它说明当前机器上平均处理能力有明显余量，但不是硬件无关的固定结论。RTF受CPU、编译选项、
系统负载和Python调度影响。

### 9.1 为什么平均RTF小于1仍可能丢块

实时麦克风每10 ms产生一块音频。即使长期平均RTF为0.05，某一次线程调度暂停超过10 ms，
仍可能出现deadline miss。因此实际demo还要观察：

- worst-case block processing time；
- queue长度是否持续增长；
- `dropped_blocks`；
- audio callback status；
- CPU高负载下是否稳定。

平均RTF是必要指标，但不是实时稳定性的全部证明。

## 11. 当前实时链路的边界

当前系统规格为：

| 项目 | 48 kHz原生链路 | 16 kHz适配链路 |
|---|---:|---:|
| 通道 | mono | mono |
| 外部chunk | 任意长度 | 任意长度 |
| RNNoise内部frame | 480 samples | 升采样后480 samples |
| 固定算法延迟 | 480 samples / 10 ms | 202 samples / 12.625 ms |
| 输出长度 | 与输入一致 | 与输入一致 |
| 状态 | 跨chunk保留 | RNNoise与两段FIR均跨chunk保留 |

尚需在具体部署平台分别测量的内容包括：

- 声卡输入buffer和设备驱动延迟；
- Python线程与queue调度抖动；
- 不同CPU负载下的worst-case处理时间；
- 长时间运行的内存与温度表现；
- 移动端、DSP或NPU上的计算和功耗。

这些不改变12.625 ms固定算法延迟，但会影响用户实际感受到的端到端延迟。

## 12. 面试快速回答

### 问：为什么不能每个chunk重新创建RNNoise state？

因为state中有GRU、Conv、pitch、overlap、delayed spectrum和上一帧增益等历史。重建state
会破坏算法连续性，结果也不再等价于官方流式处理。

### 问：如何支持任意chunk大小？

先把外部chunk追加到buffer，只要累计达到480个48 kHz样本就取一帧调用同一个C state，
不足一帧的部分留到下一次。测试证明任意切分与一次传入结果逐样本一致。

### 问：16 kHz为什么需要升到48 kHz？

因为RNNoise接口固定为48 kHz，而项目数据为16 kHz。使用状态化3倍FIR插值和抽取适配接口。
升采样不会创造8 kHz以上真实内容，只是改变采样网格并满足模型输入规格。

### 问：12.625 ms延迟如何计算？

RNNoise核心一帧延迟为160个16 kHz样本，即10 ms；两段127-tap FIR合计42个16 kHz样本，
即2.625 ms；总计202 samples，也就是12.625 ms。

### 问：离线补偿延迟是否表示实时系统没有延迟？

不是。离线裁掉前202点只是在计算指标时对齐参考时间轴。实时系统仍必须等待算法产生输出，
只能向下游报告时间戳偏移或通过整体同步管理延迟。

### 问：RTF小于1为什么还可能不实时？

RTF通常是整段平均值。实时音频要求每个callback deadline都能满足，偶发调度暂停也可能
导致queue积压或丢块，所以还要检查worst-case耗时、dropped blocks和callback status。

### 问：如何证明Python wrapper没有改变官方算法？

使用同一段int16 raw PCM分别运行官方CLI和C API wrapper，在相同量化模式下去除首个延迟
帧后，对输出PCM做逐样本相等比较；同时验证frame-by-frame、whole-file和arbitrary-chunk
三种调用方式一致。
